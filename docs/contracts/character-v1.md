# Character baseline contract v1

This is the current Phase 1 Character metadata contract. The API imports
`CharacterCreate` and `Character` from
`animation_studio/domain/v1/character.py`; `CharacterRecord` describes all five
supported persisted fields. Versioning lives in the module path and schema URI,
without a new API payload field or route.

## Published schemas

| Shape | Web URL | Model / generation mode |
| --- | --- | --- |
| POST `/characters` request | `/schemas/v1/character.create.schema.json` | `CharacterCreate`, validation |
| Created/listed character | `/schemas/v1/character.response.schema.json` | `Character`, serialization |
| Complete SQLite record | `/schemas/v1/character.record.schema.json` | `CharacterRecord`, validation |

Each export declares JSON Schema Draft 2020-12 and an ID such as
`urn:animation-studio:contracts:v1:character.record`. The files are static
schema metadata served by Vite and included in the production web build. They
contain no stored character values. The existing full API OpenAPI is unchanged.

Generate/check from the repository root using the same registry as Project:

```bash
.venv/bin/python -m scripts.export_schemas
.venv/bin/python -m scripts.export_schemas --check
```

The registry now contains six schemas: three Project and three Character.
Generated files have their own CI drift check and are excluded from Prettier.
Do not hand-edit the exports. The [Project guide](project-v1.md) also describes
publication/versioning rules; incompatible changes require a new version and
migration/compatibility checks where applicable.

## Record and API differences

Every `CharacterRecord` field is required, including nullable fields. The model
is strict, frozen and rejects unknown fields; it does not invent SQL insert
defaults for incomplete records.

| Field | Persisted record | Create request / response |
| --- | --- | --- |
| `id` | Integer primary key, normally generated by SQLite; no positive-only model constraint | Forbidden in create; required integer in response |
| `name` | Required TEXT, without SQL length or whitespace restrictions | Create: required string, trimmed before 1–120 character validation. Response: required string without trimming/length constraints |
| `description` | TEXT or NULL, SQL default NULL; raw whitespace/empty strings remain valid records | Create: optional string/null, default null; strings trimmed before the 4000-character limit. Endpoint stores empty/whitespace-only strings as NULL. Response: required key, string or null, no length restriction |
| `reference_image_paths` | TEXT or NULL, SQL default NULL; opaque text preserved exactly | Forbidden in create and absent from all character responses |
| `created_at` | Required raw text, SQL default `CURRENT_TIMESTAMP` | Forbidden in create; required string in response, without timestamp parsing |

`reference_image_paths` is **not an array contract** despite its name. Existing
values may be a single path string, JSON-looking text, malformed JSON, empty
text or NULL. The record does not parse, normalize, dereference, expose or check
the existence of those paths. A path list, uploads and provenance belong to the
later reference/character feature steps.

The create model forbids every unknown field. JSON numbers are not accepted for
name/description; the API keeps the existing non-strict Pydantic configuration.
JSON Schema captures the canonical field types/limits, but not preprocessing:
a padded 120-character name is accepted after trimming, and blank descriptions
become NULL when stored. Consumers applying schemas directly to raw input must
account for these normalization rules.

All four response keys are required, including nullable `description`. The
response model does not trim or reinterpret legacy values. Names are not unique;
duplicate names identify different records by ID. Current routes are POST and
GET-list `/characters`; a detail/update/delete endpoint, reference upload and
project assignment are not introduced.

FastAPI omits null-default annotations from OpenAPI while the exported Pydantic
create schema retains them. The response and record have no model defaults.
Schemas describe these existing differences without changing endpoint behavior.

## Existing data and limits

No SQL definition or migration changed. Upgrade/read checks use an independent
unversioned schema and each actual 0001/0002/0003 revision, then apply the current
chain twice and compare full rows exactly. Tests preserve empty/long names,
descriptions beyond current create limits, internal/outer whitespace, unusual
timestamp strings, duplicate names, and raw reference-path values. API list reads
after reopening continue to omit references, while the complete record retains them.

SQLite type affinity can admit BLOBs or other values outside the intended TEXT
domain. The strict record rejects bytes, lists and missing/non-nullable values
rather than coercing them. It is available to typed readers and verified against
stored rows; extraction does not impose new runtime validation on existing API
reads, inspect user databases or rewrite unusual values.

No new incompatibility was found for supported Character text/null records.
The previously recorded Project NULL-status API failure and the remaining
Voice/Shot/RenderJob baselines still block the full 1.17 gate. Full immutable
traits, character sheets, adapters, consent/provenance and project relations
remain in their mapped feature phases.
