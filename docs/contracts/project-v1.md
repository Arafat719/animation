# Project baseline contract v1

## 1.17f compatibility update — 2026-09-15

The response now preserves SQL NULL: Project `status`, RenderJob `state` and
`progress` accept JSON null. Omitted-field defaults and create-request validation
are unchanged. Published response schemas/OpenAPI intentionally widen these three
fields. No stored row is rewritten and no migration is needed. The UI displays
`Unknown` / `Progress unknown` and no numeric progress value for null.
The historical non-null response descriptions and HTTP 500 gap below are
superseded by this update. See [compatibility checkpoint](../null-compatibility-checkpoint.md).


This contract describes the current Phase 1 Project API and supported persisted
record values. It does not introduce the full V1 target fields or change existing
rows. The source of truth is `animation_studio/domain/v1/project.py`; the API
imports its `ProjectCreate` and `Project` models directly. Module paths and schema
URIs carry the contract version; API payloads have no new version property.

## Published schemas

The web development server and built web app expose these static JSON files:

| Shape | URL | Pydantic model / mode |
| --- | --- | --- |
| POST `/projects` request | `/schemas/v1/project.create.schema.json` | `ProjectCreate`, validation |
| Project response | `/schemas/v1/project.response.schema.json` | `Project`, serialization |
| Complete SQLite row | `/schemas/v1/project.record.schema.json` | `ProjectRecord`, validation |

Each schema declares JSON Schema Draft 2020-12 and a stable ID of the form
`urn:animation-studio:contracts:v1:project.create`. These files contain schema
metadata, never project data. The API's existing `/openapi.json` remains unchanged;
the new static files are served by the web app, not a new API endpoint. Web runtime
validation or generated TypeScript types are not introduced in this step.

Generate or check from the repository root:

```bash
.venv/bin/python -m scripts.export_schemas
.venv/bin/python -m scripts.export_schemas --check
```

CI checks for missing, modified or unexpected `.schema.json` files. Generated
files use the exporter's deterministic JSON formatting and are excluded from
Prettier; the schema check is their separate gate. Do not edit exports by hand.
Review and remove obsolete/unexpected files explicitly; generation does not
delete them. Incompatible future contract changes need a new version, migration
when needed, and compatibility tests rather than rewriting the v1 meaning.

## Field differences

All seven `ProjectRecord` fields must be present, including nullable values. It
describes a complete row, not an insert request; SQL defaults are not fabricated
when a field is missing. The record uses strict types, forbids unknown fields and
keeps timestamp text unchanged.

| Field | Persisted row | Create request / API response |
| --- | --- | --- |
| `id` | Required integer primary key; generated by SQLite on normal insert | Not a create field; response requires an integer, without a positive-ID constraint |
| `title` | Required text; no length/whitespace SQL constraint | Create: required string, 1–200 characters before trimming; endpoint rejects whitespace-only titles and stores `title.strip()`. Response: unrestricted string |
| `created_at` | Required text; SQL insert default `CURRENT_TIMESTAMP` | Absent from both API shapes |
| `updated_at` | Required text; SQL insert default `CURRENT_TIMESTAMP` | Absent from both API shapes; create explicitly sets current timestamp; no automatic update trigger is promised |
| `master_prompt` | Text or NULL; SQL default NULL | Optional string or null, default null; empty string preserved; no Project-level prompt limit |
| `target_duration_seconds` | Integer or NULL for supported rows; SQL has no range check | Create: optional integer or null, default null, 1–600 inclusive. Response: integer or null without range constraint, so legacy values are readable |
| `status` | Text or NULL; SQL insert default `'draft'`, explicit NULL stays NULL | Create/response: string, default `'draft'`; arbitrary/empty strings accepted, explicit null rejected |

API models retain Pydantic's existing non-strict behavior and ignore unknown
fields. For example, duration `"30"` becomes 30 and `true` becomes 1; the published
schema describes the canonical integer/null JSON form, not every coercible input.
JSON Schema cannot express the endpoint's title stripping/rejection rule; clients
must also reject whitespace-only titles. The fixture-job endpoint has its own
prompt validation, separate from creating a project.

Actual successful project endpoints emit all five response keys. Response model
defaults still make the last three fields optional in its model schema. FastAPI
omits null-default annotations in OpenAPI; exported Pydantic schemas retain them.
There are no renamed fields or changes to existing routes/status codes.

## Existing data and known incompatibilities

The migration chain is unchanged: `0001_initial` → `0002_job_results` →
`0003_fixture_jobs`. No new migration is needed to publish the baseline. Tests read
complete records and current API responses after upgrading disposable unversioned,
0001, 0002 and 0003 databases, with repeated initialization and exact row comparison.
Legacy whitespace, empty/long titles, unusual timestamp strings, durations outside
the create range and custom/empty statuses are preserved.

SQLite uses type affinity, not strict column types. A manually inserted REAL,
BLOB or nonnumeric TEXT in the integer-duration column is outside the supported
typed record domain; the strict record model rejects it rather than rounding or
coercing it. This model is available for typed readers and is tested against
stored rows; this step does not impose it on existing API reads or migrate such
values. The initial migration checks column definitions, not every stored value.

An existing SQL/API mismatch remains: a row with `status=NULL` is represented
losslessly by `ProjectRecord`, but the current Project API model rejects it. A
GET for that row returns 500, and a list containing it also cannot be serialized.
This behavior predates extraction; tests expose it and confirm reads do not
replace NULL with `'draft'`. It is a recorded compatibility gap to resolve before
the full 1.17 gate, not a claim that all schema-compatible databases are API-readable.

Full target fields—aspect ratio, FPS, language, style, character/voice relations
and the 30–60 second planning range—remain in their feature phases as mapped in
the [build ledger](../current-build-status.md). Other entity baselines remain
separate work.

Generation semantics: [Pydantic JSON Schema](https://docs.pydantic.dev/latest/concepts/json_schema/)
and [strict mode](https://docs.pydantic.dev/latest/concepts/strict_mode/).
