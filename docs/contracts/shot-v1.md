# Persisted Shot baseline v1

`animation_studio/domain/v1/shot.py` defines `ShotRecord`, a complete strict,
frozen record of the existing SQLite `shots` table. It rejects extra fields.
There is no Shot endpoint or request/response contract at this stage.

The Draft 2020-12 schema is published at `/schemas/v1/shot.record.schema.json`,
with ID `urn:animation-studio:contracts:v1:shot.record`. Generate/check through
`.venv/bin/python -m scripts.export_schemas`; add `--check` to verify drift.
The existing registry now publishes ten schemas; Vite copies them into builds.

## Fields

All six keys are required, even nullable `status`. SQL insert defaults are not
model defaults: an incomplete database read must fail validation.

| Field | Persisted contract | SQL behavior / limits |
| --- | --- | --- |
| `id` | Integer | Primary key, normally autogenerated; no positive-only constraint |
| `project_id` | Integer | NOT NULL; no foreign key or model lookup of a Project |
| `order_index` | Integer | NOT NULL; negative values and duplicate project/order pairs remain allowed |
| `duration_seconds` | Finite float / JSON number | REAL NOT NULL; zero, negative, fractional and large durations allowed |
| `prompt` | String | TEXT NOT NULL; empty, long and padded text preserved without normalization |
| `status` | String or null | Nullable TEXT; SQL insert default `pending`; no status enum |

SQLite REAL affinity reads inserted integral durations as floats. Pydantic's
strict float accepts integer numeric input as a float, but rejects strings and
booleans. IDs/order fields reject float and boolean coercion. Record validation
never trims text, invents defaults or checks reference existence.

SQLite can store values outside this JSON-compatible domain: BLOB/text in numeric
columns and infinity in REAL. The record rejects these; `allow_inf_nan=False`
prevents non-finite numbers from silently serializing to JSON null. JSON Schema
numbers are finite. This limitation does not introduce runtime validation or
rewrite stored rows. There is no current Shot API serialization gap to repair.

## Scope and compatibility

No SQL definition, migration, API route or existing reader changed. Tests use an
independent unversioned schema and each actual 0001/0002/0003 revision, upgrade and
reopen twice, then compare all fields and JSON serialization. Orphan project IDs,
duplicate orders, unusual status/prompt text and non-positive durations survive.
The SQL `pending` default and required nullable record key are tested separately.

This is not the Phase 3 planning `ShotPlan`: strict StoryPlan/ShotPlan fields,
duration rules, references, artifacts, attempts/errors and resumable states remain
in steps 3.1/3.5–3.8 and later media phases. No planner, endpoint or generation
feature is implied by this baseline.
